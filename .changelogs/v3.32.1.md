# Release v3.32.1

Released: 2026-08-18

## Highlights

- **`/do:next` now works on GitLab.** The same claim → worktree → ship loop that already ran on GitHub (`gh`) now runs on GitLab (`glab`) too — including self-managed and Enterprise hosts — so a GitLab repo no longer dies at the pre-flight gate after `/do:plan-task` just filed the issue.

## GitLab support in `/do:next`

- Host detection matches `/do:pr` and `/do:plan-task`: the `origin` remote decides GitHub vs GitLab; auth only confirms the matching CLI is usable. Enterprise/self-managed hosts need no extra flags.
- Every issues-mode `gh` call has a `glab` twin — listing and filtering the queue, the assignee-based claim marker and its race read-back, dependency and epic resolution, closing, and the final merge. GitLab JSON field names (`iid`, flat label strings, `username`, `opened`/`closed`) are handled explicitly rather than assumed to match GitHub's.
- GitHub's native sub-issues API has no project-scoped GitLab equivalent, so on GitLab the body task-list / `Part of #N` convention is the primary epic/child path, with `glab` forms for every command in it.
- `--self` auto-pick on GitLab filters by the authenticated `glab` username (`glab api user`), not the GitHub-CLI token `@me`, which `glab --author` does not resolve.
- `/do:plan-task` now points GitLab users at `/do:next --issues #<number>` as the next step, instead of saying that consumer is GitHub-only.
