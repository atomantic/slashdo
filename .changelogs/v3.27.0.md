# Release v3.27.0

Released: 2026-08-12

## Highlights

- **New `/do:simplify` command** — a refactor-only pass that narrows `/do:better`'s ten-dimension audit down to five (code quality, architecture, DRY/YAGNI, structural ambition, and a new cognitive-load lens), and holds every fix to a strict behavior-preservation contract so the result is a stack of `refactor:` PRs you can merge on a green test suite alone. Also available as `/do:better --simplify-only` and `/do:pr-better --simplify-only`.
- **A new cognitive-load lens** measures what a reader must hold in their head to change one line safely — flag arguments, misleading names, action at a distance, defensive fallback soup — and names the concrete transformation that removes the cost.
- **Guardrails against refactor scope creep**: the deletion test (an abstraction must concentrate complexity, not just move it), a depth-over-line-count judgment, a churn bias that skips dormant code, and a rejection record so repeat runs don't re-propose the same dead ends.
- **Behavior preservation is enforced, not assumed**: the unmodified test suite is the merge criterion, a dedicated review pass reverts any hunk that changes behavior, and every PR states its change is behavior-preserving along with the test command that verified it.

## Refactor-only audits (`/do:simplify`)
- **A refactor pass that isn't allowed to change behavior.** `/do:better` audits ten dimensions at once, which is the wrong tool when the code works and is simply expensive to read — you get security and performance PRs you didn't ask for, and the refactoring you did ask for arrives mixed in with behavioral change you now have to re-verify. `/do:simplify` narrows the same pipeline to refactoring, architecture, DRY, simplification, and cognitive load, and holds every fix to a behavior-preservation contract. The result is a stack of `refactor:` PRs you can merge on a green test suite alone.
- **Five audit agents instead of ten.** Code quality and architecture, each narrowed to its structural focus (the runtime and API-contract halves are dropped), DRY & YAGNI, structural ambition (always on — `--strict` is implied), and a new cognitive-load agent. Security, runtime bugs, performance, stack-specific gotchas, dependency removal, test authoring, and UX are out of scope for the run: not audited, not remediated, not filed.
- **A new cognitive-load lens.** It measures what a reader must hold in their head to change one line safely — mixed abstraction levels inside one function, flag arguments, names that lie, comments standing in for a rename, action at a distance, conditional ladders a lookup table would collapse, defensive fallback soup that hides which values are actually possible. Size thresholds stay with the architecture agent so the two never double-report a site. Every finding names the concrete transformation and the reader-cost it removes; formatting and import order stay the linter's job.
- **Everything else about the pipeline is unchanged** — worktree isolation, per-category PRs, CI verification, the review loop, and merge all run as usual, and every `/do:better` flag still applies. Test enhancement is the one phase skipped, since authoring tests is not a simplification.
- **Available three ways**: `/do:simplify` as its own command, `/do:better --simplify-only` (alias `--refactor-only`), or `/do:pr-better --simplify-only` to fold a refactor pass into the single PR you're already building on a feature branch.

## Keeping a refactor pass honest
- **The deletion test.** A proposed abstraction has to *concentrate* complexity behind a smaller interface, not spread it across callers. An extraction that leaves every call site passing the same arguments through one more hop is dropped — the guard against a DRY pass merging three incidental look-alikes into one abstraction now serving three masters.
- **Depth, not size.** Modules are judged by how much behavior sits behind how small an interface, not by line count. A 400-line module behind three obvious functions is fine; a 40-line one needing six parameters and knowledge of call ordering is not.
- **Churn bias.** Findings are ranked against the files people actually edit. A cleanup in dormant code drops a severity tier — tracked, but not auto-remediated — because a refactor nobody cashes in isn't worth a PR. A hot file never promotes a weak finding.
- **Rejections stick.** Reframings a run tried and rejected are recorded in the plan (or as closed labeled issues) and fed back to the next run, so repeat audits start where the last one stopped instead of re-proposing the same dead end.

## Behavior preservation
- **The test suite is the safety net, so it must keep passing unmodified.** Mechanical updates — an import path, a renamed symbol, a moved fixture — are fine. A changed assertion means the refactor moved behavior: it gets reverted, not accommodated. A test failure during verification is a regression by definition.
- **Fixes keep the same return values, side effects, error types and messages, and public API shape.** An agent that spots a real bug reports it instead of fixing it, and a moved export keeps a backward-compatible re-export at its original path.
- **A dedicated review pass reads the diff asking only "does any hunk change what this program does?"** — reverting any that do, then either deferring the finding to a run that's allowed to change behavior or recording it as a rejected reframing.
- **Each PR says so**, stating that its change is behavior-preserving and naming the test command that verified it.
