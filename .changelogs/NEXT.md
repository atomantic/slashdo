# Release vNEXT

## Highlights
- **`/do:next --swarm` now accepts an explicit issue list.** Combining `--swarm` with a target used to abort ("`--swarm` auto-picks a batch; drop the explicit target"), which made the obvious follow-up to filing a set of issues — "now go ship #12, #14 and #15 in parallel" — impossible. Name them instead: `/do:next --swarm #12 #14 #15` (or `--swarm 12,14,15`) swarms exactly those issues, in your order, with the same cherry-pick semantics a single explicit `#<num>` already had. With no target, `--swarm` still auto-picks the batch exactly as before.

## Swarm mode (`/do:next --swarm`)
- **Name the batch, or let swarm pick it.** Two or more issue numbers alongside `--swarm` become the batch itself; no target still auto-picks the first N independent eligible issues off the priority/oldest queue. One issue named runs the ordinary single-issue flow instead — a one-agent swarm is just `/do:next #12` with overhead.
- **A named list is a deliberate cherry-pick.** It overrides the auto-pick skips — parking labels like `future`/`blocked`, an active `--issues-label` filter, and blockers outside the list — and says so for each override. `--self` stays the one gate a list cannot cross: a list containing an issue someone else filed is refused before anything is claimed, rather than quietly shrinking the batch. Issues that are closed or already claimed are dropped with a reason and never swapped out for a different issue.
- **Name more issues than the concurrency cap and they ship in waves.** `--swarm=N` now caps how many run *at once*, not how many run: nine named issues with `--swarm=3` ship as three waves, each wave's merges landing before the next wave starts, so later agents branch off work that's already merged. That's also where an issue depending on (or obviously colliding with) another in your list gets placed — deferred to a later wave instead of dropped from the batch. If a predecessor's PR is left open, its dependent is held with a reason rather than started on a base missing what it needs.
- **Every number you named is accounted for.** The end-of-run summary reports each named issue with its wave and outcome — merged, PR left open, yielded to a race, skipped, or held — so a batch can never appear to have shipped work it silently dropped.
- **Cost is stated for the batch, not the agent count** (`9 issues named — ≈9× the tokens, 3 at a time`), so a long list's price is clear before any agent launches.
- **`--issues` is implied by a numbered batch.** Issue numbers are inherently tracker references, so a numbered list works even in a repo that still has a PLAN.md backlog (the switch is stated). A PLAN.md slug passed to `--swarm` still aborts — swarm has no PLAN.md path.

## Argument parsing (`/do:next`)
- **Several targets are accepted and ordered.** All non-flag tokens collect into a de-duplicated list in the order given, and a single token may carry a comma-separated run (`12,14,15`). Naming several issues *without* `--swarm` claims nothing and tells you to add `--swarm` — rather than silently spending an N× token bill you didn't ask for.
- **The agent count can't be mistaken for an issue number.** `--swarm=<N>` is always a count; the spaced `--swarm <N>` form reads the next token as a count only when it's a lone bare integer. So `--swarm 3` still means three agents, while `--swarm 12 14`, `--swarm #12 #14`, and `--swarm 12,14` all mean "swarm those two issues."
