## Swarm mode (`--swarm`) — drain several independent issues in parallel

**You are here because `SWARM` is true — this file replaces Phases 1–7 for the run.** It claims and ships up to `SWARM_N` independent open issues at once, each in its own worktree subagent, then serializes only the merge. Each agent runs the single-issue **Phases 2–6** for one issue (claim → implement → changelog → review, **no merge, no Phase 7 cleanup** — the orchestrator owns those). Swarm adds Phase A0 (reviewer preflight), Phase A (partition), and Phase C (serialized merges).

**Preconditions — check first; abort cleanly if any fails (do not partially claim):**
- **GitHub or GitLab, with the matching CLI authenticated — run `next.md`'s shared Pre-flight first** (under `## Phase 1: Pick`: host detection, and on GitLab the [next-gitlab.md](./next-gitlab.md) read and its `jq` probe). Swarm replaces Phases 1–7 but not that Pre-flight: the **A1e** (explicit-list) path never runs Phase 1, yet A1e/A2e's native blocked-by check calls `glab api ... | jq`, so every swarm path needs the probe before that check can run. On a Jira tracker the Pre-flight also runs [tracker-jira.md](./tracker-jira.md)'s, which checks the target keys.
- **A subagent-capable harness.** Swarm fans out via the harness's subagent mechanism. **If the environment cannot spawn parallel subagents, fall back to sequential** — run Phase B's per-issue task (Phases 2–6, **no merge**) one after another in this session, then Phase C so the merge stays on the serialized queue. State that you're doing so.
- **Targets are optional — and may be an explicit list.** Parse Arguments already rejected any target that isn't an issue number. Route by count: **no target** → Phase A auto-picks the batch; **two or more** → that list is the batch (Phase A's explicit-list path; the same `#<num>` cherry-pick semantics, `SWARM_N` at a time); **exactly one** → this isn't a swarm: run the single-issue **Phases 1–7** for it and say so.

**Jira tracker.** Every `#<num>` below is the issue key (`PROJ-123`): the orchestrator hands each agent a key, each branch is `next/issue-<KEY>`, and the claim, `release_marker`, and close use [tracker-jira.md](./tracker-jira.md) "Serving `/do:next`".

**Concurrency & cost.** `SWARM_N` parallel agents multiply token spend roughly N×. State the resolved N up front (e.g. `launching 3 parallel agents — ≈3× the tokens of a single /do:next`). The `1..6` clamp (Parse Arguments) is because beyond ~6 concurrent worktrees/PRs, git-index-lock contention and merge-queue churn outweigh the gain. **`SWARM_N` caps concurrency, not batch size** — an explicit list of 9 issues costs ≈9× regardless of waves, so state the total (`9 issues named — ≈9× the tokens, 3 at a time`): **for a named list of more than 8 members, stop and confirm before launching wave 1** — print the total cost and the wave plan, and proceed only on an explicit go-ahead. Below that threshold, state the cost and continue. (Non-interactive/subagent context: proceed, but log the total prominently.)

### Swarm Phase A0 — Reviewer preflight (orchestrator, before partitioning)

Run once per invocation, after argument resolution and the single-target routing above, and before Phase A partitions work or anything is claimed. It exists to catch a reviewer that cannot start at all before every worker discovers that separately, and it spends no reviewer tokens. (A later Phase A fallback to one eligible issue runs the normal single-issue flow, which has no preflight.)

1. **Resolve the review plan once** with [multi-reviewer-loop.md](./multi-reviewer-loop.md)'s parser and defaults, keeping the requested entries and settings as given; do not substitute reviewers. With no external review selected (including `--no-review`), the preflight is empty.
2. **Check each entry without calling a model**, optional (`~opt`) entries included, since a missing optional CLI would otherwise fail inside every worker. The binary or alias must exist (that file's step 5 check; `cmd[<invocation>]` has no fixed binary and passes), and where the CLI has an offline login/status subcommand (`codex login status`, `claude auth status`) it must report logged in. PR-side reviewers (`copilot`, `@<login>`) pass on the code-host authentication the Pre-flight confirmed; never open a probe PR. Quota, provider-admission and input-size failures only appear in a real review and are left to each worker's normal handling, and a missing tool-free mode is not a failure.
3. **Record `REVIEWER_PREFLIGHT`**: one row per entry with the reviewer and its resolved model/effort (show a `cmd` entry by its safe label, not its raw invocation), whether it is optional, `available` or `unavailable`, and the reason. The rows are valid for this invocation only and are handed to workers as data, never read from the repository.
4. **If a required entry is unavailable, stop now**, before any worker, worktree or claim, and print the reviewer, the reason and the remedy (install it or log it in) with Phase D's reviewer summary. An unavailable optional entry stays in the plan as a recorded skip. An available entry has only been shown to start; it still reviews each worker's branch.

### Swarm Phase A — Triage & partition (orchestrator, in the main repo)

**Two paths in.** With **no target**, run **A1–A2** (auto-pick). With an **explicit list of two or more issue numbers**, skip the picker and run **A1e–A2e** instead. Both paths converge on **A3** and hand Phase B an ordered batch, split into waves of at most `SWARM_N`.

1. **A1 — Build the eligible queue by running `next.md`'s `### Phase 1 — issue queue`; it applies every skip and filter. Do not invent a second picker. An `epic-wrapup` is eligible.**
2. **A2 — Select the first `SWARM_N` *independent* eligible issues** off the top of that ordered queue:
   - **Intra-batch dependency.** If a candidate declares `Depends on #N` / `Blocked by #N` (or native blocked-by) on **another candidate in the batch**, keep only the predecessor this round — the successor self-clears and is picked next run once the predecessor merges. (Blockers *outside* the batch were already handled by the Phase 1 skip.)
   - **File-overlap avoidance (best-effort).** From each issue's title/body, predict the rough files/paths/components it touches. When two candidates obviously target the same file(s), keep the higher-priority one and skip the other **this round** — not for correctness (the serialized merge + re-sync handles that) but to avoid two agents thrashing or duplicating the same file. This is a cheap heuristic, not a guarantee; note when you apply it.
   - **Under-fill is fine.** If fewer than `SWARM_N` independent issues exist, run the swarm at the smaller size and say so. **If only one is eligible, run the normal single-issue flow instead** (Phases 1–7) and say so — a one-agent swarm is just `/do:next` with overhead.

   Auto-pick never selects more than `SWARM_N`, so it always yields exactly **one wave**.

**A1e — Vet each named issue; no picker, no substitutions.** As with a single explicit `#<num>`, a named issue overrides parking labels, active filters and open blockers outside the list; state each override, and keep the issue's own dispatch hint for Phase B. Check each named issue in this order:
   - **`--self` and `--collaborators` are the gates a list cannot cross.** When `SELF_MODE` is on, verify every named issue's author is the running account (the same check as Phase 1 step 5) — an issue that **doesn't exist or can't be read** falls through to the drop rule below rather than the refusal, so a typo'd number is a skip, not a bogus "filed by someone else". Refuse the whole run only when a real issue resolves to another author: ``Issue #<num> was filed by <author>, not you — /do:next --self only works on issues you filed. Drop --self, or drop #<num> from the list.`` When `COLLAB_MODE` is on and `SELF_MODE` is not (SELF_MODE already proved `@me`, which is a collaborator), verify every named issue's author is in the trusted claim pool (live collaborators plus `--trusted-authors`, the same check as Phase 1 step 5) — same exist-or-unreadable fallthrough. Refuse the whole run only when a real issue resolves to someone in neither set: ``Issue #<num> was filed by <author>, who is not a collaborator on <owner/repo> (and not on --trusted-authors) — /do:next --collaborators only claims collaborator-authored issues. Drop --collaborators, or drop #<num> from the list.`` Don't quietly drop it and swarm the rest — a silently shrunk batch hides a refused security gate.
   - **Closed, or no such issue → drop with a note** (`#<num>: already closed — skipping`).
   - **In flight or already assigned → drop with a note** (`#<num>: already claimed (branch/PR/assignee) — skipping`). Require `next.md`'s shared `CLAIM_ID=<N> fresh_claim_check`, including same-login assignment and GitHub PR body/head-commit evidence; never adopt an existing branch.
   - **Marked `in-progress` with no assignee, no `issue-<num>` branch and no PR → adopt the reservation.** That is a bare label reservation: whoever queued the issue for this run (the user, or the planner that filed it) marked it so no other claimer would take it first. Naming it is the same deliberate override as naming a parked issue, so check it with `CLAIM_RESERVED=1 CLAIM_ID=<N> fresh_claim_check`, say `#<num>: adopting its in-progress reservation`, and record it in `RESERVED`. Any assignee, branch or PR beside the label is a real claim and drops the issue as above. A failed/incomplete PR evidence read aborts before any worker, worktree or marker. **Never substitute another issue for a dropped one** — the user named these; auto-pick is not in play.
   - **Epic → resolve with Phase 1 step 3** and act on the state: an `epic-wrapup` joins the batch like any issue; an `epic-done` is closed inline and dropped from the batch; an `epic-open` joins the batch only as an explicit override (say that children are still open).
   - **Nothing survives → stop** and list why per issue. **Exactly one survives → run the single-issue flow** (Phases 1–7) for it and say so.
**A2e — Order the batch and split it into waves.** Keep the user's order (a named list is a stated preference, so never re-sort it by priority) except where these constraints require otherwise:
   - **A member that depends on another member** (`Depends on #N` / `Blocked by #N`, or native blocked-by) goes in a later wave than its predecessor. Phase C merges each wave before the next starts, so the dependency is satisfied by the time the dependent's agent branches. Members in a dependency cycle cannot be ordered; drop them with a note so a human can break it.
   - **A member whose listed blocker will not ship in this run is held, not run.** That is a blocker the user named that is still open but was dropped in A1e (in flight or assigned), dropped as a cycle member, or is itself held. Record it for Phase D (`#21 held: depends on #17, which is not shipping in this run`). A closed or missing blocker holds nothing.
   - **Members that obviously touch the same files** go in different waves (the same best-effort prediction as A2); note it.
   - **Chunk into waves of at most `SWARM_N`**, keeping each deferred member in a strictly later wave than what it waits on, so a wave may come out smaller than `SWARM_N`. Count the issues that survived A1e, not the targets named. State the plan up front: `9 issues survived vetting, 3 at a time — 3 waves (≈3× the tokens of a single /do:next per wave)`.
   - **Reserve every member (GitHub/GitLab; skip on Jira, which has no label marker).** A named member sits unmarked from the moment it passes A1e until its worker assigns itself: a minute or two in wave 1, and as long as the earlier waves take after that. Any other claimer (a second `/do:next`, a scheduled agent) could take an issue the user named for this run in that window. For each member not already in `RESERVED`, immediately after its A1e check passed, run `label_ensure in-progress FFA500 "Claimed and being worked"` and `label_add <num> in-progress`, and record it in `RESERVED`. The label is the whole reservation: no assignee and no branch, so the worker's own claim still runs its race read-back. A failed `label_add` leaves the member unreserved; say so and continue. A member held in this step is not reserved.
**A3 — Do not claim here (both paths).** Each issue is claimed *inside* its own subagent so the assignee-marker + race read-back runs per issue, atomically. The orchestrator only hands each agent one specific issue number, and says whether it is in `RESERVED`.

### Swarm Phase B — Fan out (one subagent per issue)

Launch the current wave's agents in parallel (issue all the sub-agent launches together rather than one at a time) and wait for all of them to return.

**Apply each issue's dispatch hint to its own agent.** Read its `model${LABEL_SEP}<tier>` / `effort${LABEL_SEP}<level>` labels, splitting on `$LABEL_SEP` (A1's queue already carries labels; for A1e fetch them with `issue_labels <num>`), and resolve them through [model-tiers.md](./model-tiers.md). A missing label inherits the session setting for that axis. If the dispatch is rejected for lack of entitlement, retry once on the session model and note the degrade; if the host cannot set a per-agent model or effort, run at the session default and report the hint in Phase D. These labels are separate from the `--model`/`--effort` filters and from `--review-models`.

Give each subagent exactly one issue number and this task:

> Run the `/do:next` single-issue flow for issue **#`<num>`** — the **Phase 1 explicit-`#<num>` path** (for validation + variable setup) followed by **Phases 2 through 6 only** — in your own sibling worktree, with these adjustments:
> - **Validate & set up via Phase 1's explicit-number path first:** run Phase 1's `#<num>` branch to confirm the issue is open and not in flight, resolve it if it's an epic, and set `ISSUE_NUM=<num>` / `SLUG=issue-<num>` — Phase 2's worktree/branch and every later host-verb call depend on those variables. (Skip the auto-pick walk; the orchestrator already vetted this issue in Phase A, and an explicit number deliberately bypasses the auto-pick skips.) **Map this validation's failures to the structured result instead of the explicit-path's normal print-and-stop:** if it fails because the issue is now **in flight or already assigned** (a sibling `/do:next` claimed it between Phase A and now — a lost race, not an error), return `{ issue, status: "yielded" }`; if it fails because the issue is **closed or no longer exists**, return `{ issue, status: "skipped", reason }`. Either way, do not pick a different issue.
> - **A reserved issue** (the orchestrator says so) already carries `in-progress` from this run's own reservation: run every ownership gate for it as `CLAIM_RESERVED=1 CLAIM_ID=<num> fresh_claim_check`, and do not treat that label as another run's claim. An assignee, an `issue-<num>` branch or an open PR is still a lost race. For an issue that was not reserved, the label means what it always does.
> - **Then claim via that same explicit-number path:** it performs the Phase 2 worktree creation + assignee-marker claim with the race read-back. If the read-back shows a sibling won the race, **yield** (release the marker, retract the claim branch, clean up your worktree) and return `{ issue, status: "yielded" }` — do not pick a different issue.
> - **Phase 3 still applies:** if the issue is stale/superseded/awaiting-input, skip it (release the marker, clean up) and return `{ issue, status: "skipped", reason }`.
> - **Use the supplied `REVIEWER_PREFLIGHT` rows** with the resolved review settings. A reviewer whose row is `unavailable` and optional is not launched or retried: record it as `skipped` with the row's reason; an optional skip or inconclusive result stays out of the aggregate, as `~opt` already means. Every other reviewer runs normally on its own recipe, and one with no matching row gets the normal checks. A required reviewer marked `unavailable` should have stopped the swarm before any worker; if one reaches you, stop as inconclusive. If no external reviewer ran (none selected, or all skipped this way) and the Local Code Review gate passed, return `opened-no-review`; otherwise return the normal aggregate. Required review failures, unresolved findings, build or test failures and unpushed fixes still block. Include the rows in `notes`.
> - Implement (Phase 4) and record completion + changelog (Phase 5) as normal.
> - **Ship via `/do:pr --no-merge`** with the run's review flags (Phase 6) and **stop before the merge** — open the PR, run the review gate, but do not merge and do not run Phase 7 cleanup. The orchestrator owns the merge and the cleanup.
> - **Wait on external reviewers and CI actively; do not end your turn to "wait for a notification."** You are a subagent: if you stop while a background reviewer (`codex review`, `claude -p`, `agy`) or a CI watch is still running, your run is over — completion notifications are not guaranteed to reach a stopped subagent, and the orchestrator reads your last words as the final result while the reviewer's findings are lost. Wait with bounded foreground shell calls, each safely under the host's foreground time limit (about 10 minutes), repeated until the reviewer's exit code is recorded (the local CLI runner's `wait` subcommand does exactly this for a reviewer it launched) — then issue the same call again if it is still running. End your turn only to return the structured result below.
> - **Return a structured result**, one of two shapes Phase C dispatches on by whether `pr_number` is present:
>   - **PR opened:** `{ issue, pr_number, branch, worktree, review_status, notes }`, where `review_status` is `/do:pr`'s aggregate (`clean` / `partial` / `inconclusive` / `dirty`) or `opened-no-review` when no external reviewer ran and the Local Code Review gate passed.
>   - **No PR** (claim yielded to a race winner, or Phase 3 skipped it as stale): `{ issue, status: "yielded" | "skipped", reason }` — no `pr_number`.

Pass each agent the `REVIEWER_PREFLIGHT` rows, the resolved review settings and the review flags (`--review-with` / `--review-iterations` / `--review-mode` / stop-mode / `--reviewer-applies`; a run-level `--no-review` goes to workers as `--review-with none`), plus the orchestrator's resolved `--self|--no-self`, `--collaborators|--no-collaborators` and `--trusted-authors <list>|none`. The fix regression guard lives in `/do:pr`'s review loop, so it applies inside each agent; CI flake handling runs in Phase C's merge gate. Concurrent `git worktree add` calls against the shared repo can briefly contend on `.git` index locks; an agent that hits a transient lock retries once before failing.

**Harness without parallel subagents?** Run this same per-issue task **sequentially** in the current session — identical task body — then Phase C unchanged. Sequential fan-out only loses concurrency. **The dispatch hints degrade to reports here**, as in the single-issue flow (Phase 1 step 6): note each issue's hint and run in the current session.

**Multi-wave batches.** Run B → C once per wave, in wave order: merge wave *K*'s PRs before launching wave *K+1*, so the next wave's agents branch from a default branch that already carries the earlier work. Phase D runs once, after the last wave, over the accumulated results. Restate progress between waves (`wave 2/3 — #17 #21 #23`). If a wave leaves an issue unmerged for any reason (PR left open, agent yielded, skipped as stale, or the agent never returned), continue with the next wave but hold any later member that A2e placed behind that issue for a dependency, since its blocker is still open (`#21 held: depends on #17, which did not merge this run`). Members deferred only for file overlap still run.

### Swarm Phase C — Serialized merge queue (orchestrator)

After the barrier, merge the wave's returned PRs **one at a time, never concurrently** — each merge advances the default branch, so the next PR may need a re-sync. Walk the results in the batch's own order: priority/oldest for an auto-picked batch, the **user's order** for an explicit list (A2e). For each:

1. **Skip non-mergeable results.** A result with `status: "yielded"`/`"skipped"` (no `pr_number`) has nothing to merge — record it. For the rest, apply **single-issue Phase 6's review gate** to `review_status`: never merge `dirty` (build/test broken) or `inconclusive` (a non-optional reviewer missing/timed-out/errored) — leave that PR open and record why; merge only `clean`, `opened-no-review` (Local gate passed, no external reviewer ran), or `partial` **with** an explicit `--review-stop-on-*` flag. (Agents that never returned are reconciled in Phase D, not here.)
2. **Re-sync onto the advanced default branch only when it overlaps the PR** — from the PR's worktree, `git fetch origin <default>`; when the base-only commits (`git diff --name-only HEAD...origin/<default>`) touch any file the PR changes (`git diff --name-only origin/<default>...HEAD`), such as the shared changelog, run `git merge --no-edit origin/<default>`; otherwise keep the validated HEAD — resolving any changelog conflict **deletions-win** (a line removed on either side stays removed; keep additions from both). If the merge **can't be resolved cleanly**, leave that PR open, record it for human follow-up, and move to the next — **never force it**.
3. **Merge through the shared merge gate.** Each swarm agent opened its PR with `/do:pr --no-merge`, so no CI gate has run yet, and any step-2 re-sync produced a new SHA that the gate's wait mode pushes and then waits on. Resolve `MERGE_METHOD` (gate step 1) **once per invocation**, before the first merge, and reuse it for every PR in the batch. Run the gate from the orchestrator with these inputs: `{PR}` is `<pr_number>`, `{GIT}` is `git -C "<worktree>"`, `{MODE}` is `wait`, `{LINKED_WORKTREE}` is `1`, and `{MERGE_METHOD}` is the `MERGE_METHOD` from Parse Arguments. After a confirmed merge, the gate's step 5 deletes the remote head (the `branch` the worker returned). Phase D removes the worktree and the local branch from the main repo. If the gate returns **queued** or **left open**, leave that PR open, record why, and move on to the next PR:

!read lib/merge-gate.md

4. **Close out the issue — only when step 3 read back `MERGED`.** A PR the merge left open or queued has shipped nothing, so closing its issue would drop live work out of the queue: record it as left-open with the reason instead, and let Phase D keep its worktree and branch. For a genuinely merged PR, apply single-issue Phase 7's closure step: confirm `Closes #<num>` auto-closed it on merge to the default branch; if still open, run `issue_close_note <num> "Shipped in PR #<pr_number>."`. Then run `label_rm "$ISSUE_NUM" in-progress`. On Jira, that step is [tracker-jira.md](./tracker-jira.md) "Close after merge" with the PR's URL; a failed transition is recorded for Phase D, and the queue moves on.

### Swarm Phase D — Reconcile, clean up, report

Runs **once per invocation**, after the last wave, over every result the batch produced.

1. **Sweep worktrees & branches** from the main repo: `git worktree remove` + `git branch -d`/`-D` each merged agent's worktree/branch, then `git worktree prune`. **Keep** the worktree/branch of any PR left open so the work can be finished.
2. **Handle agent death / spend-limit.** If an agent never returned (crash, monthly spend cap), reconcile from **tracker state, not its last words** — and **never assume a review status survived the death** (slashdo's local-reviewer verdicts aren't persisted to the PR, so there's no stored `review_status` to read back). A worktree/branch/PR may exist:
   - **A PR opened:** recompute its gate from scratch before merging — re-run the run's review flags and the same `REVIEWER_PREFLIGHT` block against it (`/do:pr --no-merge` with the same `--review-with`), or, when no external review was selected, repeat the Local Code Review gate and treat green required-CI + a mergeable state as `opened-no-review`-eligible. Merge it through the Phase C queue only on a clean recompute; if required external reviewers can't be re-run to clean, leave the PR open and flag it for a human.
   - **No PR:** run `release_marker`, then delete the local and remote `next/issue-<num>` branch; flag the issue for human follow-up.
   - **PR opened, but its recomputed gate is not clean and you cannot finish it:** leave the PR open and keep its worktree and branch so a human can continue; flag the issue for follow-up.
3. **Release unused reservations.** For every issue in `RESERVED` whose worker never claimed it (held behind an unmerged blocker, never launched, or its worker returned `yielded`/`skipped` or died before assigning itself), run `label_rm <num> in-progress` unless the issue now has an assignee, which means someone holds a real claim. A run that stops early for any reason does this before it exits. A reservation the run could not release is an open issue with `in-progress`, no assignee and no `issue-<num>` branch: name each one in the summary so it can be unlabelled by hand.
4. **Re-evaluate parent epics** for every issue that closed — a shipped issue may have been an epic's last child (the Phase 7 "re-evaluate the parent epic" step, run once per closed child).
5. **Reconcile changelog churn.** Parallel claims all touch the same changelog file, when the project has one; the deletions-win re-syncs in Phase C should have kept it consistent — confirm the merged default branch's changelog carries every shipped issue's entry with no duplicate or resurrected lines. Skip this check for a project whose release notes come from commit messages.
6. **Print a summary table** — one row per batch issue, including the ones dropped in A1e and any held in a later wave: `issue · wave · dispatch (model/effort actually used, or `session` when the issue carried no hint — or when this host couldn't set them) · PR · result (merged / open: why / yielded / skipped / held / needs-input) · review status`. The dispatch column is what makes a wrong hint visible: a `model:light` issue whose agent needed three review iterations is a label to correct, not a mystery. For an explicit list, **account for every number the user named** — a named issue that never ran must appear with its reason, never be silently absent.

**Reviewer summary (also on an A0 stop):** one line per resolved reviewer — `reviewer · model/effort · required/optional · available/unavailable (reason, remedy) · what workers did (reviewed / skipped / run stopped)` — or `no external review selected`. For a merged issue whose external reviewers were all optional and all skipped or inconclusive, say `merged without external review — optional reviewers unavailable or inconclusive`; the preflight never approved any code.
