## Multi-Reviewer Loop

Orchestrate one or more reviewers (`copilot`, `codex`, `agy`, `claude`, `grok`, `pi`, `cursor`, `opencode`, `ollama`, `cmd[<invocation>]` for a harness not in this list, or an arbitrary GitHub login `@<login>`) against the same branch / PR. Each reviewer runs its own single-reviewer loop; GitHub-side reviewers share `github-reviewer-loop.md`, with Copilot adding its small delta. This wrapper iterates the ordered list and decides when to stop.

**Series (default) vs parallel — `{REVIEW_MODE}`.** In series each reviewer completes (review → fix → verify → push) before the next starts, so later reviewers see earlier reviewers' *committed fixes* and can catch a regression a fix introduced; that is why the list is **ordered** — put the cheapest/highest-signal reviewer first. The opt-in `parallel` mode runs every reviewer's **review** concurrently against one frozen baseline, then applies the deduped union of findings once: faster, but **no reviewer sees another's fixes**. Do NOT run reviewers concurrently unless `{REVIEW_MODE}=parallel` was explicitly resolved.

### Inputs

The calling command must populate these before reaching this loop:

- `{REVIEW_AGENTS}` — ordered list of reviewer slugs, e.g. `[codex, agy, copilot]`; may be a single entry. `gemini` and `antigravity` normalize to `agy`; `cursor-agent` to `cursor`; `zen` and `opencode-zen` to `opencode`. Deduped left-to-right after normalization; first occurrence wins. A **model-taking** entry (`codex`, `claude`, `agy`, `grok`, `pi`, `cursor`, `opencode`, or `ollama`) may carry a bracketed model selector `<agent>[<model>]` (e.g. `codex[o3]`, `claude[claude-opus-4-8]`, `agy[Gemini 3.8 Flash (High)]`, `grok[grok-code-fast-1]`, `cursor[gpt-5]`, `opencode[provider/model]`, `ollama[qwen2.5-coder:32b]`), which the parser strips into a per-entry model string: `{OLLAMA_MODEL}` for the Ollama loop (empty → auto-select), `{REVIEW_MODEL}` for the local-agent loop (`codex`/`claude`/`agy`/`grok`/`pi`/`cursor`; empty → their CLI defaults; `opencode`; empty → no slashdo model override, so use an explicitly selected or configured supported provider/model). `copilot` and `@<login>` take **no** model bracket. An `@<login>` entry targets an arbitrary GitHub reviewer (user or App/bot); the parser strips the leading `@` into a per-entry `{REVIEWER_LOGIN}` (`@octocat` → `octocat`) for the GitHub-reviewer loop. The `[<model>]` selector and the login are part of the dedup identity (`codex[a]` / `codex[b]` and `@octocat` / `@org-review-bot` are distinct; two bare `ollama`s or two `@octocat`s, compared lowercased, collapse to one). The full token grammar, suffixes included, is:

  ```
  entry := ( <agent> [ "[" <model> "]" ] | "cmd[" <invocation> "]" | "@" <login> ) ( "~opt" | "~max=" <n> | "~effort=" <level> )*
  ```

  All three suffixes are optional, order-independent, and repeat-free (at most one of each); see the three bullets below.

  **`cmd[<invocation>]` — an arbitrary reviewer not in the fixed slug list.** For a harness slashdo hasn't hardcoded a recipe for (a Pi/Ollama combination, a wrapper script, anything with its own headless CLI), `<invocation>` is the operator's own shell command — a specific string the user typed or saved, never derived from repo content, a PR body, or anything else an attacker could influence, since it runs via `bash -c`. The contract: it must read the review prompt on **stdin** and print the same `NO FINDINGS` / `FINDING <N>:` verdict every local-agent reviewer emits (see [local-agent-review-loop.md](./local-agent-review-loop.md)) — wrap a harness that wants the prompt as a flag or file in a small script that bridges stdin to it. `cmd` dispatches through the local-agent loop exactly like `agy`/`grok`/`cursor`: since an opaque command's isolation can never be verified, it **always** runs review-only with the orchestrator applying fixes, regardless of `--reviewer-applies` — there is no escalation path, unlike `codex`'s verified sandbox. There is no separate `[<model>]`/`~effort=` handle for `cmd` — the model/effort tuning (harness, runtime, provider, model, effort, or whatever axes the invocation itself exposes) belongs inside the invocation string. The **full invocation string, verbatim, is the entry's identity** for dedup — two different `cmd[...]` values are distinct reviewers, never collapsed as one, and are reported/logged as `cmd:<first whitespace-delimited token of the invocation>` (e.g. `cmd:pi`) rather than the full command line. **Sources:** a `cmd[…]` entry is honored only from the command line or the global `~/.claude/.slashdo-config.json`; one read from a per-project `.slashdo.json` — repo content, committed and editable by anyone who can open a PR — is dropped with a warning by the saved-defaults step and never reaches this loop (see `lib/review-config-defaults.md`). **Rendering:** wherever this wrapper prints a reviewer list — the `Review plan:` banner, the `Note: deduped --review-with list to …` line, `Reviewers planned/run`, the per-pass table — a `cmd` entry appears as its `cmd:<first token>` label, never the raw invocation (which may embed a key or token the operator baked in).
- `{REVIEW_MODELS}` — optional per-agent **default-model map** resolved from saved config (the `review-models` key, project-over-global merged per agent — see `~/.claude/lib/review-config-defaults.md`). Keys are agent slugs (`codex`/`claude`/`agy`/`grok`/`pi`/`cursor`/`opencode`/`ollama`); values are model strings. It supplies an entry's model **only when that entry's `--review-with` token carried no `[<model>]` bracket**. Absent/empty when no saved default resolved. Precedence per entry, top wins: explicit `<agent>[<model>]` bracket → `{REVIEW_MODELS}[slug]` → the reviewer's built-in default for other local agents, or no slashdo model override for `opencode`.
  - **Optional (non-blocking) marker `~opt`.** `ollama~opt`, `ollama[qwen2.5-coder:32b]~opt`, `@some-bot~opt`, `copilot~opt` mark that reviewer **optional**: it is still requested, still runs, and its findings are still fixed, but an *inconclusive* result (timeout / skipped / incomplete / no-verdict) is **excluded from the merge gate** — it never flips `{OVERALL_STATUS}` to `inconclusive`, so never blocks `--merge`. Use it for reviewers that don't reliably return a verdict (e.g. a local Ollama model). The parser strips `~opt` into a per-entry boolean `{OPTIONAL}` (default `false`) **before** slug/`[model]`/`@login` parsing; it is **not** part of the dedup identity (`ollama~opt` ≡ `ollama`). Not exempted (see the aggregate rules): a hard-error (`cli-error`/`broken-build`/`test-failed`/`rejected`) and `push-failed` — a broken tree, or fixes stranded locally, still block. `~opt` is shell-metacharacter-free so a `--review-with` value stays inert in a command string.
  - **Per-reviewer iteration cap `~max=<n>`.** `claude~max=2`, `ollama[qwen2.5-coder:32b]~max=1`, `@some-bot~max=3`, `copilot~max=0` cap how many **review → fix → re-review cycles** that reviewer runs. The per-entry form of `--review-iterations`, but it applies to **every** reviewer type, including the local agents and `ollama` whose caps are otherwise fixed at 3 — so `--review-with claude~max=2,ollama~max=1,codex~max=3` budgets each reviewer separately. `<n>` must be a **non-negative integer**: `n ≥ 1` runs at most `n` cycles (still exiting early on a clean round or convergence); `0` means "loop until that reviewer is clean", bounded by each inner loop's 10-iteration safety guardrail. Stopping at an explicitly configured `~max=<n>` (n ≥ 1) with work outstanding returns `capped` (clean-equivalent for the merge gate); exhausting a *built-in* cap returns `guardrail` (inconclusive) — see `capped` under Series dispatch. Chains freely with `~opt` and `~effort=<level>` in any order (`ollama~opt~max=1~effort=high` ≡ `ollama~effort=high~opt~max=1`); at most one `~max=` per entry; not part of the dedup identity; shell-metacharacter-free.
  - **Per-reviewer reasoning effort `~effort=<level>`.** `codex[gpt-5.6-luna]~effort=max`, `claude~effort=high`, `ollama[qwen2.5-coder:32b]~opt~effort=low` set that reviewer's reasoning effort; `<level>` must be one of `low`, `medium`, `high`, `xhigh`, `max`. The parser strips it into a per-entry `{ENTRY_EFFORT}` (default: unset/empty) **before** slug/`[model]`/`@login` parsing. Not part of the dedup identity; when duplicates collapse, the effort comes from the first occurrence that carried a `~effort` (`first-occurrence-wins`).
- `{REVIEW_STOP_MODE}` — one of:
  - `all` (default) — run every listed reviewer in order, regardless of what each reports
  - `on-findings` — stop after the first reviewer that produced a verdict status (`clean`, `capped`, or copilot `too-large`) AND added at least one commit since `PASS_START_SHA` (the orchestrator actually landed a fix). Reviewer-reported "comments" without resulting commits do NOT trigger the stop — the signal is the commit-graph delta, not the count of suggestions
  - `on-clean` — stop after the first reviewer that reports zero findings (clean)
- `{REVIEWER_APPLIES}` — boolean, forwarded to each reviewer's loop. No effect on the copilot path.
- `{REVIEW_ITERATIONS}` — non-negative integer (default 1), forwarded to the **copilot** and **`@<login>`** loops as their review-and-fix cycle cap; each still exits early when a review returns 0 comments. `0` means "loop until 0 comments" (legacy, bounded by each loop's 10-iteration safety guardrail). No effect on the local-agent loop (`codex`/`agy`/`claude`/`grok`/`pi`/`cursor`/`opencode`/`cmd`) or the Ollama loop, which keep their own fixed caps. A per-entry `~max=<n>` **overrides this flag for that entry** — see the cap-resolution step in Pre-flight.
- `{GH_HOST}` — the GitHub API host derived from the repo's `origin` remote (see `~/.claude/lib/gh-host.md`), forwarded to the GitHub-side inner loops (`copilot`, `@<login>`) so their `gh api` calls target the right host on GitHub Enterprise. Empty/absent on GitLab or when unset means "let `gh` use its github.com default."
- `{WAIT_SCHEDULE}` — the calling command's schedule for the current GitHub-side entry. Resolve it by reviewer kind before dispatch and pass only that selected schedule to the shared GitHub-reviewer template; local-agent and Ollama entries do not use it.
- `{REVIEW_MODE}` — `series` (default) | `parallel`. `series` runs each reviewer's full single-reviewer loop one at a time, in list order; the next starts only after the previous one's fixes are committed and pushed. Stop-modes and `--reviewer-applies` work as documented. **Use it unless the caller explicitly resolved `parallel`.** Only when `{REVIEW_MODE}=parallel` was explicitly resolved (flag or saved default), read the parallel-mode pre-flight incompatibility warnings, dispatch algorithm, and aggregate-status rule now — they replace Pre-flight step 6, Series dispatch, and the parallel clause of Aggregate report below for this run. Series callers never need it.

### Pre-flight

1. **Validate the list is non-empty.** If empty, abort with `--review-with requires at least one agent`.
2. **Strip the `~` suffixes, then validate each slug.** For each entry, strip **every** trailing `~`-suffix — `~opt` into `{OPTIONAL}` (default `false`), `~max=<n>` into `{ENTRY_MAX}` (default: unset, "no per-entry cap requested"), `~effort=<level>` into `{ENTRY_EFFORT}` (default: unset/empty). Strip from the **right**, repeatedly, so the suffixes may appear in any order and the remaining token is suffix-free before slug/`[model]`/`cmd[…]`/`@login` parsing. Validate each `~max` value as a **non-negative integer** and each `~effort` value as one of `low`, `medium`, `high`, `xhigh`, `max`; reject anything else — including a repeated `~max=` or `~effort=` on one entry, or an unknown `~`-suffix — with `Invalid --review-with suffix on {entry}: ~max must be a non-negative integer and ~effort must be one of low, medium, high, xhigh, max, each appearing at most once; the only suffixes are ~opt, ~max=<n>, and ~effort=<level>.` The `[<model>]`/`cmd[<invocation>]` bracket is stripped *after* the suffixes and its free-form value may itself contain a `~`, so match suffixes only outside the outermost brackets. The same applies to the list separator: split the value on `,` only outside the outermost brackets — a `,` inside `cmd[…]` (or inside a `[<model>]`, e.g. `cursor[claude-opus-4-7[thinking=true,effort=high]]`) is part of the value, not a new entry. "Outermost" means the **first `[` and the last `]` of the token**: a `~` suffix is recognized only after that last `]`, so `cmd[a]~opt[b]` is the invocation `a]~opt[b` with no suffix, never `a` plus `~opt`. Reject a `cmd` entry whose brackets are unbalanced, whose invocation contains a newline, or whose invocation is empty/whitespace-only, with the unknown-value abort — every parser (this loop, `/do:config`, `lib/better-options.md`) applies this one rule so the string an operator saw validated is byte-identical to the one handed to `bash -c`. Then validate the remaining slug is one of `copilot`, `codex`, `agy` (aliases `gemini` / `antigravity`), `claude`, `grok`, `pi`, `cursor` (alias `cursor-agent`), `opencode` (aliases `zen` / `opencode-zen`), `ollama`, `cmd` (**requires** a non-empty bracket — bare `cmd` with no `[<invocation>]` is invalid, since there is nothing to run), each of `codex`/`claude`/`agy`/`grok`/`pi`/`cursor`/`opencode`/`ollama` optionally carrying a `[<model>]` bracket, or an arbitrary GitHub login `@<login>`. Abort on the first unknown value with `Unknown --review-with value: {value}. Use one of: codex, agy, claude, grok, pi, cursor, opencode, ollama, copilot, cmd[<invocation>], @<login> (each optionally suffixed ~opt, ~max=<n>, and/or ~effort=<level>).` Normalize `gemini`/`antigravity` → `agy`, `cursor-agent` → `cursor`, `zen`/`opencode-zen` → `opencode`. For a model-taking entry with a `[<model>]` bracket (the value is the substring between the outermost `[` and `]`, free-form — spaces and parens allowed, e.g. `agy[Gemini 3.8 Flash (High)]`, `opencode[provider/model]`; `copilot[…]` and `@login[…]` are invalid — reject with the unknown-value abort), record its model string — `{OLLAMA_MODEL}` for `ollama` (empty for bare `ollama` → auto-select), `{REVIEW_MODEL}` for the rest — but **keep the bracket attached to the entry as its identity** so step 3 does not collapse `codex[a]` and `codex[b]`. **For a `cmd[<invocation>]` entry**, the bracket is not a model — it is the entire invocation, recorded verbatim (whitespace and case preserved, since it is a shell command) as `{REVIEWER_CMD}`; empty (`cmd[]`) is invalid, same abort. For an `@<login>` entry, strip the leading `@` into `{REVIEWER_LOGIN}` and validate it against `^[A-Za-z0-9][A-Za-z0-9-]*(\[bot\])?$` (GitHub user charset plus the optional `[bot]` App suffix); reject a malformed login with the same unknown-value abort. Keep the full login as the entry's identity.
3. **Dedupe** preserving first-occurrence order. Compare on the normalized identity: the slug, plus the `[<model>]` selector for a model-taking entry, the **verbatim `<invocation>`** for a `cmd[…]` entry (case- and whitespace-sensitive, since it is a shell command — not normalized like other identities), and the lowercased `{REVIEWER_LOGIN}` for `@<login>` entries (GitHub logins are case-insensitive) — so `gemini`/`agy`, two bare `ollama`s, and `@Octocat`/`@octocat` are duplicates; `codex[a]`/`codex[b]`, `ollama[a]`/`ollama[b]`, two `cmd[…]` entries with different invocation text, and `@octocat`/`@org-review-bot` are distinct. No `~` suffix is part of the identity — `ollama~opt`, `ollama~max=2`, `ollama~effort=high` and `ollama` are all duplicates. When duplicates collapse, the survivor is **optional if *any* collapsed occurrence was marked `~opt`** (optional-wins), and takes its `{ENTRY_MAX}` and `{ENTRY_EFFORT}` from the **first** occurrence that carried each. Print a warning if duplicates were dropped: `Note: deduped --review-with list to {final list}.`
   - **Resolve each entry's effective model** after dedupe, for every model-taking entry: a `[<model>]` bracket wins; else `{REVIEW_MODELS}[normalized slug]` if present; else empty. Empty means the reviewer's built-in default — `codex`/`claude`/`grok`/`pi`/`cursor` fall back to the CLI's own default model, `agy` to its pinned default (the newest `* Flash (High)` entry in `agy models`, overridable via `AGY_REVIEW_MODEL`), `opencode` receives no slashdo model override and therefore requires an explicit or configured supported provider/model (the formerly documented Zen free-tier model is not an implicit default), `ollama` to auto-select. Store the result as the entry's `{REVIEW_MODEL}` (or `{OLLAMA_MODEL}` for `ollama`) for dispatch; no inner loop re-implements this precedence. **`cmd` has no model to resolve here** — `{REVIEW_MODEL}`/`{REVIEW_MODELS}` never apply to it; whatever model tuning its invocation needs is already baked into `{REVIEWER_CMD}`.
   - **Resolve each entry's effective iteration cap** after dedupe, for **every** entry. Precedence, top wins:
     1. the entry's `{ENTRY_MAX}` (from its `~max=<n>` suffix), when it carried one;
     2. `{REVIEW_ITERATIONS}` — **only for the GitHub-side reviewers** `copilot` and `@<login>`. It never reaches a local-agent or `ollama` entry, so `--review-iterations 5 --review-with ollama` still leaves ollama on its built-in cap; `~max` is the only way to move it;
     3. the inner loop's built-in default — `1` for `copilot`/`@<login>`, `3` for the local-agent loop and the Ollama loop.

     Store the result as the entry's `{MAX_ITERATIONS}`, plus a boolean `{MAX_EXPLICIT}` that is true only when the value came from source 1 or 2 (the user chose this ceiling). `{MAX_EXPLICIT}` is what lets an inner loop distinguish `capped` (a configured budget was spent — clean-equivalent) from `guardrail` (a built-in backstop cut off a still-productive loop — inconclusive).
4. **Validate stop-mode flags are not combined.** `--review-stop-on-findings` and `--review-stop-on-clean` are mutually exclusive; if both are present, abort with `--review-stop-on-findings and --review-stop-on-clean cannot be combined`.
5. **Probe binary availability** for each **local** agent: `command -v {binary}`, where `{binary}` is the agent's executable name (`claude`, `codex`, `agy`, `grok`, `pi`, `cursor`, `opencode`, or `ollama`). The `agy`/`gemini`/`antigravity` slugs all probe the `agy` binary, `zen`/`opencode-zen` both probe the `opencode` binary, `cursor`/`cursor-agent` both use the **Cursor binary probe** in `lib/local-agent-review-loop.md` (prefer `cursor-agent`; fall back to `agent` only when that binary identifies as Cursor — Grok Build also ships an `agent` on `$PATH`), and a bracketed `<agent>[<model>]` entry probes its **base** agent's binary (`codex[o3]` → `codex`, `ollama[...]` → `ollama`, `grok[grok-code-fast-1]` → `grok`, `cursor[gpt-5]` → the Cursor probe, `opencode[provider/model]` → `opencode`). **Skip the probe for the GitHub-side reviewers `copilot` and every `@<login>` entry** — they review cloud-side via authenticated `gh` (the calling command already confirmed `gh` auth). **`cmd[<invocation>]` has no fixed binary to probe** — `{REVIEWER_CMD}` is an arbitrary shell command whose own executable(s) are opaque to this pre-flight; the inner loop records a command-not-found (`bash -c` exit `127`/`126`) as `skipped` at dispatch time — the same status this probe assigns a missing fixed binary — and any other launch failure as `cli-error`. For any local agent whose binary is missing:
   - **Default mode**: print a warning (`{agent} CLI not installed — recording as skipped`) and **keep the agent in `REVIEW_AGENTS`** so it appears in the per-pass table; when the dispatch loop reaches it, short-circuit the inner loop and record the pass with status `skipped` (preconditions not met). This propagates into `{OVERALL_STATUS}=inconclusive` per the aggregate rule — the user asked for that reviewer's perspective and didn't get it. **Do not silently drop** (that would let `{OVERALL_STATUS}=clean` when a requested reviewer never ran), and **do not append `copilot` (or any other reviewer) as a fallback** — the executed list must never contain a reviewer the user didn't ask for.
   - **Interactive mode (`--interactive`)**: ask the user whether to install, skip (record as `skipped` as above), or abort. If install succeeds, proceed normally; if skip, leave it in the list to be recorded as `skipped`; if abort, exit the wrapper.
   Swarm callers (`/do:next --swarm`): [next-swarm.md](./next-swarm.md#swarm-phase-b--fan-out-one-subagent-per-issue)'s Phase B defines how a worker consumes an orchestrator-supplied `REVIEWER_PREFLIGHT` block to short-circuit this probe for a matching entry. Single-issue callers never supply it and this step behaves as written above.

Only when `{REVIEW_MODE}=parallel` was explicitly resolved, apply [multi-reviewer-parallel.md](./multi-reviewer-parallel.md)'s Pre-flight step 6 here.

Print the resolved plan before starting: `Review plan: {REVIEW_AGENTS} (mode: {REVIEW_MODE}, stop-mode: {REVIEW_STOP_MODE})`. When any entry resolved a non-default cap, append the per-reviewer caps: `Iteration caps: claude=2, ollama=1, codex=3`.

### Series dispatch (default — `{REVIEW_MODE}=series`)

Iterate `REVIEW_AGENTS` in order, running each reviewer's full single-reviewer loop to completion (review → fix → verify → push) before starting the next. For each `{REVIEW_AGENT}`:

1. **Print a banner**: `--- Review pass {n}/{N}: {REVIEW_AGENT} ---`
2. **Capture baseline**: `PASS_START_SHA=$(git rev-parse HEAD)` so the wrapper can tell whether this reviewer changed anything, independent of the inner loop's own tracking.
3. **Dispatch** to the matching single-reviewer loop. The loop file lives under the host CLI's lib directory (`~/.claude/lib/` for Claude, `~/.config/opencode/lib/` for OpenCode) or bundled alongside the skill under `lib/` (for Antigravity, Codex, Grok — read on demand per the directive in this skill). Forward this entry's resolved `{MAX_ITERATIONS}` and `{MAX_EXPLICIT}` to **every** target — that pair is what carries a `~max=<n>` into the reviewer — and `{ENTRY_EFFORT}` as `{REVIEW_EFFORT}` / `{OLLAMA_EFFORT}` (empty if unset):
   - `copilot` → `{LIB_DIR}/github-reviewer-loop.md` plus `{LIB_DIR}/copilot-review-loop.md` (forward `{GH_HOST}`, the caller-selected `{WAIT_SCHEDULE}`, and this entry's `{MAX_ITERATIONS}` as its `{REVIEW_ITERATIONS}` iteration cap)
   - `@<login>` → `{LIB_DIR}/github-reviewer-loop.md` (forward `{GH_HOST}`, the caller-selected `{WAIT_SCHEDULE}`, this entry's `{REVIEWER_LOGIN}`, and this entry's `{MAX_ITERATIONS}` as its `{REVIEW_ITERATIONS}` iteration cap)
   - `codex` | `agy` | `claude` | `grok` | `pi` | `cursor` | `opencode` → `{LIB_DIR}/local-agent-review-loop.md` (forward this entry's resolved `{REVIEW_MODEL}` — empty means the CLI's built-in default for the other local agents, but no slashdo model override for `opencode` —, `{REVIEW_EFFORT}` — empty means CLI/session default —, and its `{MAX_ITERATIONS}`, the loop's built-in `3` unless a `~max=<n>` moved it; the `--review-iterations` flag itself never reaches this loop)
   - `cmd` → `{LIB_DIR}/local-agent-review-loop.md` (forward `{REVIEWER_CMD}` — the verbatim invocation — in place of `{REVIEW_MODEL}`/`{REVIEW_EFFORT}`, which don't apply, and its `{MAX_ITERATIONS}`; always dispatched review-only, `{REVIEWER_APPLIES}` is ignored for this entry)
   - `ollama` → `{LIB_DIR}/ollama-review-loop.md` (forward this entry's `{OLLAMA_MODEL}` — empty means auto-select —, `{OLLAMA_EFFORT}` — empty means unset —, and its `{MAX_ITERATIONS}`, built-in `3` unless a `~max=<n>` moved it; `{REVIEWER_APPLIES}` does not apply — the Ollama loop is always review-only, and the `--review-iterations` flag never reaches it)

   The inner loop handles its own iterations, fix-and-push cycles, and verification, and returns a `{STATUS}`:
   - Copilot loop: `clean | capped | timeout | error | guardrail | too-large`
   - GitHub-reviewer loop (`@<login>`): `clean | capped | timeout | not-requestable | error | guardrail` (`timeout` = requested but no review submitted within the wait; `not-requestable` = the request failed and no review appeared — both inconclusive, not eligible to merge)
   - Local-agent loop: `clean | capped | no-verdict | guardrail | cli-error | broken-build | test-failed | rejected | skipped` (`no-verdict` = the reviewer ran but its output was not a parseable verdict or OpenCode was denied provider admission — inconclusive, not a hard error, so it does not short-circuit the remaining reviewers and IS excused by `~opt`; `skipped` = the reviewer never launched — a missing binary, or for `cmd` a command-not-found exit — also inconclusive and excused by `~opt`)
   - Ollama loop: `clean | capped | incomplete | guardrail | cli-error | broken-build | test-failed | rejected | skipped` (`incomplete` = the diff was only partially reviewed — some files' review invocations failed, or their diff exceeded the per-file budget and was truncated — inconclusive, not eligible to merge)

   `capped` means the same in all four loops: the reviewer reached an **explicitly configured** iteration budget (`{MAX_EXPLICIT}` true — a `~max=<n>` suffix, or `--review-iterations` on a GitHub-side pass) after applying every fix it surfaced; it is **clean-equivalent for the merge gate** — the user asked for `n` rounds and got them. `guardrail` is the opposite and stays inconclusive: a *built-in* ceiling (the local-agent / Ollama default of 3, or the 10-iteration safety backstop in `~max=0` mode) cut off a loop that was still landing substantive findings.
4. **Record the pass result** (status + number of new commits since `PASS_START_SHA` + this entry's `{OPTIONAL}` flag) as a per-pass row for the aggregate report.
5. **Assert the pass's fixes reached the remote.** Every inner loop pushes its own fix commits as its final step, but nothing downstream re-checks it — an orchestrator that improvises a loop body instead of running it step by step leaves the fixes committed *locally*, where `gh pr create` and the merge gate never see them, while every reviewer still reports `clean`/`capped` and CI still passes on the stale pushed tree. Verify it here, once, for every reviewer type:

   ```bash
   # Skip entirely when there is no upstream to compare against: /do:review and
   # /do:better can run on a branch that was never pushed, and a detached HEAD or a
   # missing origin fails this the same way. This is a "did the push step run" check,
   # not a "must have a remote" requirement.
   if git rev-parse --abbrev-ref --symbolic-full-name @{u} >/dev/null 2>&1; then
     UNPUSHED="$(git log --oneline @{u}..HEAD)"
   else
     UNPUSHED=""   # no upstream — nothing to assert
   fi
   # Derive the push target from CONFIG, not by splitting the abbrev-ref: a remote
   # name may itself contain a slash (`up/stream/main`), and a LOCAL upstream
   # (`branch.<n>.remote=.`, what `git branch --set-upstream-to=main` produces)
   # abbreviates to a bare `main` with no slash at all — a `%%/`+`#*/` split mangles
   # both into a bogus remote. Empty on a detached HEAD, which skips the check.
   BR="$(git branch --show-current)"
   PUSH_REMOTE="$(git config --get "branch.$BR.remote")"
   PUSH_BRANCH="$(git config --get "branch.$BR.merge")"   # already a full refs/heads/<name>
   if [ -z "$PUSH_REMOTE" ] || [ "$PUSH_REMOTE" = "." ]; then
     UNPUSHED=""   # upstream is a local branch (or none) — no remote to assert against
   fi
   # Scope it to THIS pass. A pass that committed nothing has nothing of its own
   # stranded, so anything ahead of the upstream predates the pass — deliberately
   # unpushed local work the caller never asked this loop to publish. Use `if`, not
   # `[ … ] && …`: as the block's last statement a false test would exit non-zero and
   # read as a failed command to the orchestrator running this snippet.
   if [ "$PASS_START_SHA" = "$(git rev-parse HEAD)" ]; then
     UNPUSHED=""   # pass committed nothing — nothing of its own is stranded
   fi
   # Push in the SAME shell that derived the target — these variables do not survive
   # across separate Bash invocations, and an empty PUSH_REMOTE would push to the
   # empty-string remote: a fatal error, reported as a bogus push-failed.
   if [ -n "$UNPUSHED" ]; then
     if ! git push "$PUSH_REMOTE" "HEAD:$PUSH_BRANCH"; then
       # A conflict is a resolution handoff, not push-failed. The caller MUST apply
       # rebase-conflict-resolution.md and rerun this config-derived block before it
       # records a status or dispatches the next reviewer.
       if git pull --rebase --autostash; then
         git push "$PUSH_REMOTE" "HEAD:$PUSH_BRANCH"
       else
         echo "REBASE_CONFLICT_NEEDS_RESOLUTION"
         false
       fi
     fi
   fi
   ```

   If `UNPUSHED` was non-empty the inner loop's push step did not run, and the block above already attempted to push it — `git push "$PUSH_REMOTE" "HEAD:$PUSH_BRANCH"`, retried once behind `git pull --rebase --autostash` on a non-fast-forward, the same retry the loop files use. **Run the whole thing as one block**: `PUSH_REMOTE`/`PUSH_BRANCH` live only in the shell that set them. `REBASE_CONFLICT_NEEDS_RESOLUTION` is a handoff to the orchestrator, not the block's final result: while Git reports an active rebase or unmerged paths, do **not** record `push-failed` and do not dispatch another reviewer. Read and follow [rebase-conflict-resolution.md](./rebase-conflict-resolution.md), complete the rebase and its focused validation, then rerun this entire config-derived block so the variables and destination are fresh. Only a non-conflict pull error, the playbook's last-resort abort after a genuine ambiguity, or a push that still fails after the completed resolution becomes `push-failed`.

   **Push to the ref the upstream names — not a bare `git push`, and not `git push origin HEAD`.** A bare push fans out under `push.default=matching` to every same-named local branch (including a `release` branch that may auto-tag and publish) and errors under `push.default=nothing`. `git push origin HEAD` resolves `HEAD` to the **local** branch name and pushes to `refs/heads/<local-name>`, ignoring the upstream — on a branch whose upstream has a different name (or lives on another remote) it creates a spurious remote branch, leaves the real PR head stale, and `@{u}..HEAD` is *still* non-empty afterward (issue #134's exact failure, reintroduced by the guard meant to prevent it). `branch.<name>.merge` is already fully qualified, so the destination is `HEAD:$PUSH_BRANCH`, never `HEAD:refs/heads/$PUSH_BRANCH`.

   If the push still fails, **record the pass as `push-failed`** and print the unpushed SHAs. This overrides whatever status the inner loop returned — **except a hard-error** (`cli-error`/`broken-build`/`test-failed`/`rejected`), which keeps its own status so the hard-error short-circuit still fires and the aggregate stays `dirty` (note the stranded SHAs in that pass's Notes instead); downgrading it to `push-failed` would make the aggregate `inconclusive` and let a caller like `/do:pr` — which aborts only on `dirty` — open a PR against a branch it was supposed to refuse.

   Three properties of this check:
   - **`git status` is not a substitute.** A clean working tree says nothing about committed-but-unpushed commits; compare against the upstream ref specifically.
   - **It is posture-agnostic.** It applies unchanged when `{REVIEWER_APPLIES}=true` — that flag changes who *edits*, not who *pushes*.
   - **It only ever pushes *forward*, and only this pass's own work.** Never a force-push, never a rewrite of what the remote has, never pre-existing local commits on a pass that committed nothing. A faithfully-executed hard-error pass (`broken-build`/`test-failed`/`rejected`) already reverted to its start commit with `git reset --hard`, so `PASS_START_SHA == HEAD` and the check is a no-op — but still **run** it on a hard-error pass, since an improvised loop body may have skipped the revert.

### Stop-mode decision

After each pass completes (before moving to the next reviewer), evaluate `{REVIEW_STOP_MODE}`:

| Mode | Continue to next reviewer when... | Stop when... |
|------|------------------------------------|---------------|
| `all` | always (until list exhausted) | list exhausted |
| `on-findings` | this pass is inconclusive (status ∈ `timeout`/`error`/`guardrail`/`no-verdict`/`skipped`/`not-requestable`/`push-failed`), regardless of whether commits were added; OR this pass returned a verdict status (`clean` or `capped` for any loop, or `too-large` for copilot) AND made zero changes (`PASS_START_SHA == HEAD`) | this pass returned a verdict status AND made any change (commits added since `PASS_START_SHA`) |
| `on-clean` | this pass returned a non-clean status (including inconclusive, and including `capped` from any loop — which means the configured iteration budget ran out with fixes applied, not a confirming clean re-review) OR made changes | this pass returned `clean` (or copilot `too-large`) AND made zero changes |

**Hard-error short-circuit (applies in all modes)**: if the inner loop returns `cli-error`, `broken-build`, `test-failed`, or `rejected`, stop the multi-reviewer loop immediately — the branch is in a state subsequent reviewers shouldn't run against (broken build / reverted state / explicit reject). Surface the failing reviewer's status as the wrapper's overall status.

Inconclusive non-fix statuses (`copilot` `timeout`/`error`/`guardrail`, the GitHub-reviewer (`@<login>`) `timeout`/`not-requestable`/`error`/`guardrail`, local-agent `guardrail`/`no-verdict`, ollama `incomplete`, plus the `skipped` precondition statuses) do NOT count as findings — the reviewer couldn't produce a verdict. OpenCode's sanitized provider-admission diagnostic is one of these `no-verdict` outcomes. Treat them as continue-signals in every stop mode, even if the inner loop added commits before bailing out: a stop-mode short-circuit requires a *verdict* status (`clean`, `too-large`, `capped`) before the commits-added / no-commits-added condition is honored, so a flaky reviewer that crashed mid-fix cannot claim the "found something" signal.

**`push-failed` is a continue-signal too.** Step 5 overrides a pass's status to `push-failed` when its fix commits could not be published; since it is not a verdict status it can never satisfy a stop-mode short-circuit — a pass whose fixes are stranded locally must not be the reason the remaining reviewers are skipped.

**Convergence within a single reviewer.** The stop-mode governs *which reviewers* run and in what order — the user's explicit choice, never second-guessed here. How long *one* reviewer keeps re-reviewing its own fixes is owned by each inner loop's re-loop step via the convergence gate (`~/.claude/lib/review-convergence-gate.md`): a reviewer converges — stops re-requesting — once a round lands only marginal/edge-case findings, well before its mechanical iteration ceiling. So a `clean`/`capped` return may reflect diminishing returns rather than an exhausted cap; it is still a verdict status for stop-mode purposes. The gate never causes the wrapper to skip a reviewer the user listed.

Only when `{REVIEW_MODE}=parallel` was explicitly resolved, run [multi-reviewer-parallel.md](./multi-reviewer-parallel.md)'s Parallel dispatch section instead of the Series dispatch above.

### Aggregate report

After the wrapper exits, print a summary block per pass:

```
## Multi-Reviewer Summary

Review mode: {REVIEW_MODE}
Stop mode: {REVIEW_STOP_MODE}
Reviewers planned: {original REVIEW_AGENTS list}
Reviewers run:     {actually executed subset}

| Pass | Agent  | Optional | Iterations | Status        | Commits added | Notes                     |
|------|--------|----------|------------|---------------|---------------|---------------------------|
| 1    | codex  | no       | 2/3        | clean         | 2             | log: /tmp/local-review-…  |
| 2    | ollama | yes      | 1/1        | capped        | 1             | non-blocking (~opt), ~max=1 |
| 3    | copilot| no       | 0/1        | too-large     | 0             | PR exceeded 20k-line cap  |

Overall status: {OVERALL_STATUS}
```

The **Optional** column reflects each pass's `{OPTIONAL}` flag (from a `~opt` suffix): an `inconclusive` status on an optional row did **not** contribute to a merge-blocking aggregate, so the summary shows why a merge proceeded despite a reviewer that returned no verdict.

The **Iterations** column is `{rounds actually run}/{MAX_ITERATIONS}` for that pass (`{MAX_ITERATIONS}` renders as `∞` when the cap is `~max=0`); `1/1` says the reviewer stopped because it spent exactly the budget it was given. Name the source in Notes when a per-entry `~max=<n>` set the cap.

A `push-failed` row must name the inner loop's original status and list the stranded SHAs in Notes (e.g. `clean, but 2 commits unpushed: a1b2c3d, e4f5a6b`).

**Optional passes are excluded from the `inconclusive` determination.** A pass whose `{OPTIONAL}` is true and whose status is inconclusive (`timeout`/`error`/`guardrail`/`no-verdict`/`skipped`/`not-requestable`/ollama `incomplete`) is treated as clean-equivalent *for the aggregate only* — it never contributes to `{OVERALL_STATUS}=inconclusive`, so it never blocks `--merge`. An OpenCode provider-admission denial remains explicitly visible as `no-verdict`; optionality only removes its merge-blocking effect. Two things optionality does **not** excuse:

- **A hard-error.** If an optional reviewer returns `cli-error`/`broken-build`/`test-failed`/`rejected`, the hard-error short-circuit still fires and the aggregate is still `dirty`.
- **`push-failed`.** An optional reviewer's *findings* are still real fixes, and a `push-failed` pass means those fixes are committed only on this machine. `~opt` says "don't block the merge on this reviewer's missing verdict"; it does not say "merge a tree that isn't the reviewed tree." So `push-failed` contributes to `{OVERALL_STATUS}=inconclusive` regardless of `{OPTIONAL}`.

`{OVERALL_STATUS}` is computed by evaluating each rule top-down; the first matching rule wins:
- `dirty` — the wrapper stopped due to a hard-error short-circuit (`cli-error`, `broken-build`, `test-failed`, `rejected`); the failing pass's status is the proximate cause. **Applies regardless of the pass's `{OPTIONAL}` flag.**
- `inconclusive` — the executed list contains at least one **non-optional** pass whose status is inconclusive (`timeout`, `error`, `guardrail`, `skipped`, `not-requestable` — an `@<login>` whose request failed and never reviewed — `no-verdict` — a local agent that ran but did not answer in the verdict format — or ollama `incomplete` — a partially-reviewed diff), **or any pass at all — optional included — whose status is `push-failed`** (that pass's fixes are committed locally but never reached the remote, so the reviewed tree is not the tree a merge would land), regardless of whether other passes returned `clean`. Passes marked `~opt` are ignored here **for the inconclusive statuses listed first** — but never for `push-failed`, which lands the aggregate here regardless of `{OPTIONAL}`. `skipped` covers preconditions-not-met cases — e.g., `codex` in `/do:review` PR mode (codex review --base only accepts a git ref) or `copilot` when no PR exists for the branch. E.g. `--review-with copilot,codex` where copilot times out and codex returns clean is `inconclusive` — the user asked for both perspectives and got one; so is the all-inconclusive case (a lone `copilot` that times out). Distinct from `dirty` (build is fine) but still **not eligible to merge** — the user must re-run or intervene
- `partial` — some passes were skipped due to a stop-mode decision (`on-findings` or `on-clean` short-circuit) AND every executed pass returned a clean-equivalent status — `clean`, copilot `too-large`, or `capped` from any of the four loops (a `~max=<n>` pass that lands fixes and returns `capped` is exactly what trips `on-findings`, so excluding it would leave that run matching **no** rule) — OR was an excluded optional-inconclusive (no *non-optional* inconclusive remaining)
- `clean` — every **non-optional** executed pass returned `clean` (or copilot `too-large`, or `capped` from any of the four loops — an explicitly configured cap, per `capped` under Series dispatch; a *built-in* cap that stops a productive loop is `guardrail`, which lands in the rule above), every **optional** pass returned `clean` or an excluded-inconclusive status, AND no hard-error short-circuit fired AND no *non-optional* inconclusive statuses remain AND **no pass at all — optional included — returned `push-failed`** (top-down evaluation already routed such a pass to `inconclusive`; stating it here keeps the `clean` rule true on its own terms) AND no stop-mode short-circuit fired

**In parallel mode, use [multi-reviewer-parallel.md](./multi-reviewer-parallel.md)'s Aggregate report — parallel mode addendum instead of this top-down rule** — the same statuses, evaluated over each reviewer's review-phase result plus the single apply step rather than per-pass fix-and-push results.

The calling command (do:pr / do:release / do:review) uses `{OVERALL_STATUS}` to decide its next action. For do:release the merge gate must require `{OVERALL_STATUS}=clean` — never merge on `dirty` or `inconclusive`, and on `partial` only when the stop-mode was explicitly set (the user opted into the short-circuit).
